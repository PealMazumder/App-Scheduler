# 07 — UX & Accessibility (Audit Phase 7)

**Date:** 2026-09-04 · branch `claude-audit` @ `be0f508`
**Scope:** all 29 files / 1,749 lines under `app/src/main/java/com/peal/appscheduler/ui/`, plus
`MainActivity.kt`, `AndroidManifest.xml`, `res/values/{strings,colors,themes}.xml`, `res/drawable/*`.
**Coverage: 100% of the UI layer was read line by line.** No sampling.

**Method.** Static reading + greps. `lintDebug` (39 warnings, per `00-baseline.md`) reported **zero**
a11y issues — Android Lint's Compose accessibility coverage is thin, so every finding below comes from
reading, not from lint. **No device or emulator was available**, so nothing here was confirmed by
TalkBack, Accessibility Scanner, a font-scale sweep, or a screenshot. Findings that depend on rendering
are marked **unverified** with the measurement that would settle them.

---

## Summary

The app is three screens with no text input, no bottom bar, and no adaptive layout. The a11y surface is
therefore small — and about half of it is wrong. The serious problems are not the classic missing
`contentDescription` ones (those are mostly present); they are:

1. **Two undismissable permission dialogs that can lock the user out of the app entirely** (UX-1).
2. **Blank screens instead of empty/error states**, including an infinite spinner on the device-apps
   list (UX-2, UX-3).
3. **The Scheduler screen's Save button becomes unreachable** at large font scale or in landscape
   because the screen doesn't scroll (UX-4).

Genuinely fine: `android:supportsRtl="true"` is set and the layout code is direction-agnostic
throughout (`padding(horizontal=)`, `Arrangement.Start`, `Alignment.Start`; zero `left`/`right` usage);
dynamic color is correctly wired for Android 12+; all text sizing is in `sp`; no screen is locked to
portrait. Hardcoded strings are **5 total**, not the sprawl a 33-line `strings.xml` suggests — the
localisation discipline is better than expected.

## Findings

### UX-1 — Permission dialogs cannot be dismissed and re-arm on every resume — **Critical**

`CommonAlertDialog.kt:16-50` defaults to `showDismissButton = false`, `dismissOnBackPress = false`,
`dismissOnClickOutside = false`. **Both call sites use the defaults**, so each dialog renders with a
single "Grant Permission" button, no cancel, no back, no scrim tap.

- `MainActivity.kt:53-66` — an `onResume` observer sets `showDialog = !Settings.canDrawOverlays(context)`.
  Confirm sends the user to the overlay settings screen; if they come back without granting,
  `ON_RESUME` fires and the dialog reappears. **The user cannot reach the app without granting
  `SYSTEM_ALERT_WINDOW`**, and cannot decline.
- `SchedulerScreen.kt:116-144` — identical pattern for `SCHEDULE_EXACT_ALARM` on the Scheduler screen.

**Impact:** a user who declines an intrusive permission is hard-blocked out of the product with no exit
other than force-stop or uninstall. There is no rationale text explaining *why* the permission is
needed beyond "This app needs permission to display over other apps." Also a Play policy exposure
(gating all functionality on `SYSTEM_ALERT_WINDOW` — see the security phase for whether the permission
is needed at all).

### UX-2 — Device-apps list shows an infinite spinner on error and a blank screen when empty — **High**

`DeviceAppsViewModel.kt:45`:

```kotlin
.catch { e -> e.printStackTrace() }
```

The exception is swallowed and `isLoading` is **never reset to false**. `DeviceAppsRepositoryImpl.kt:24-40`
calls `packageManager.queryIntentActivities(...)` and `loadIcon(...)` for every launcher app in a single
binder round-trip — a documented source of `TransactionTooLargeException`/`DeadObjectException` on
devices with many apps. When it throws, the user sits on `CommonCircularProgressIndicator` forever.

`DeviceAppsListScreen.kt:57-64` is a `when { isLoading -> …; deviceApps.isNotEmpty() -> … }` with **no
`else`**. Not-loading + empty list renders nothing at all. There is no error state in
`DeviceAppsContract.State` (`DeviceAppsContract.kt:8-12`) to render even if one were wanted.

**Impact:** unrecoverable dead-end on the app-selection screen, which is the only entry point to the
core task. Violates CLAUDE.md non-negotiable #8 (don't catch and swallow).

### UX-3 — Home screen has no empty state; first launch is a blank white screen — **High**

`HomeScreen.kt:76-92` renders a bare `LazyColumn` over `homeScreenState.scheduledApps`. On first
install the list is empty, so a new user sees an entirely empty screen with a single unlabelled "+"
FAB and no explanation of what the app does. `HomeContract.State.isLoading` (`HomeContract.kt:9`) exists
but `HomeViewModel` never sets it `true` — it only ever sets it `false` at
`HomeViewModel.kt:48`, so the loading branch is dead code and there is no loading state either.

`HomeViewModel.kt:43-54` also collects `getScheduledAppUseCase()` with no `catch`, so a Room failure
propagates out of `viewModelScope.launch` uncaught rather than surfacing an error state.

**Impact:** the app's first-run impression is a blank page. Empty and error are both undesigned.

### UX-4 — Scheduler screen doesn't scroll; Save is unreachable at large font scale — **High** (unverified)

`SchedulerScreen.kt:146-207` is a `Column(modifier.fillMaxSize().padding(16.dp))` with
`verticalArrangement = Arrangement.spacedBy(16.dp)` and **no `verticalScroll`**. Its content —
"App" title, a 68dp app row, "Scheduling" title, two picker rows, and the action buttons, plus 5×16dp
of spacing — is roughly 300dp at default font scale. At 200% font scale, or in landscape on a phone,
the terminal `ActionButtons` row (`SchedulerScreen.kt:198`) is laid out past the bottom edge and
clipped, with no way to scroll to it.

**Impact:** the Save button — the only way to complete the app's single task — becomes untappable for
users with large text, and possibly in landscape. **Unverified:** confirm with
`adb shell settings put system font_scale 2.0`, or add `@Preview(fontScale = 2f, heightDp = 360)` to
`SchedulerScreenPreview` (`SchedulerScreen.kt:365`).

### UX-5 — Past dates and times are freely selectable; rejection only happens after Save — **High**

`DatePickerDialog.kt:26` uses a bare `rememberDatePickerState()` with no `selectableDates` constraint,
so yesterday and last year are selectable. `TimePickerDialog.kt:24-27` seeds from `LocalTime.now()` but
imposes no lower bound. The only guard is post-hoc, in the ViewModel:
`SchedulerViewModel.kt:152` compares against `System.currentTimeMillis()` and emits
`Effect.PastDateTime`, surfaced as a **Toast** at `SchedulerScreen.kt:327-333`.

**Impact:** for a scheduling app, the primary input control actively permits invalid input and reports
the error in the most dismissible, least accessible channel available. The correct affordance
(`SelectableDates` with `isSelectableDate`) is one parameter away.

### UX-6 — Picker dialogs discard the currently scheduled date/time when editing — **Medium**

`DatePickerDialog.kt:26` — `rememberDatePickerState()` takes no `initialSelectedDateMillis`, and
`TimePickerDialog.kt:23-27` initialises from `LocalTime.now()` rather than from state. Neither dialog
receives the current selection; `SchedulerScreen.kt:209-227` passes only callbacks. Editing an existing
schedule (`state.isEditable`, `SchedulerViewModel.kt:61`) therefore opens both pickers blank/now
instead of at the saved value.

Compounding this: `DatePickerDialog.kt:31-39` guards the confirm action with
`selectedDateMillis?.let { … }`. Because nothing is preselected, tapping **OK** before choosing a date
does nothing at all — the dialog stays open with a button that appears broken.

**Impact:** edit flow silently loses context; a dead-looking OK button on first open.

### UX-7 — Nested Scaffolds double-apply system bar insets on Home — **Medium** (unverified)

`MainActivity.kt:68-72` wraps the whole app in a `Scaffold` and passes
`Modifier.padding(innerPadding)` down to `AppSchedulerNavHost`, which forwards the same modifier to
every screen (`AppSchedulerNavHost.kt:35-56`). `Modifier.padding` **does not consume** the insets —
there is no `consumeWindowInsets` anywhere in the codebase (grep: zero hits for `consumeWindowInsets`,
`WindowInsets`, `safeDrawing`, `imePadding` outside the single `enableEdgeToEdge` import).

`HomeScreen.kt:63` then opens a **second** `Scaffold` inside that already-padded region. Its default
`contentWindowInsets` still reports the full `safeDrawing` insets, so `paddingValues` at
`HomeScreen.kt:79` adds status-bar and nav-bar padding a second time.

Per the `edge-to-edge` skill (Step 3), the outer Scaffold should `consumeWindowInsets(innerPadding)`,
or the inner Scaffold should not exist.

**Impact:** visible dead space above and below Home content, and a FAB floating noticeably high off the
navigation bar. **Unverified:** confirm with a screenshot on a 3-button-nav device, or Layout Inspector.

### UX-8 — Lists apply insets as `Modifier.padding` instead of `contentPadding` — **Medium**

`HomeScreen.kt:76-80` and `DeviceAppsListScreen.kt:73-77` both apply inset padding to the `LazyColumn`'s
*modifier*. The `edge-to-edge` skill is explicit: "DO NOT apply it as a `Modifier.padding()` to the
list's parent container, as this clips the content and prevents it from scrolling behind the system
bars."

**Impact:** on an edge-to-edge app (targetSdk 36 — opt-out is unavailable), scrolled list content is
hard-clipped at the inset boundary instead of passing under a translucent nav bar. Cosmetic, but it is
the exact anti-pattern the platform guidance names.

### UX-9 — Touch targets on the date/time picker rows are ~24dp tall — **Medium**

`SchedulerScreen.kt:161-177` (time) and `SchedulerScreen.kt:180-196` (date) are
`Row(Modifier.fillMaxWidth().clickable { … })` whose tallest child is a default 24dp `Icon` alongside a
`bodyLarge` `Text` (24sp line height). The row's measured height is therefore ~24-28dp, well under the
48dp minimum. Because these are raw `Modifier.clickable` on a `Row` and not Material components, they
get no `minimumInteractiveComponentSize` for free.

**Impact:** the two controls that drive the app's core task are half the minimum tappable height.
`Modifier.heightIn(min = 48.dp)` fixes both. **Unverified as a measurement**, but the composition is
unambiguous from reading; Accessibility Scanner would flag it directly.

### UX-10 — Clickable rows carry no semantic role, click label, or merge — **Medium**

Three interactive rows use bare `Modifier.clickable` with no `role`, no `onClickLabel`, and no
`Modifier.semantics(mergeDescendants = true)`:

- `ScheduledAppItem.kt:41-44` — TalkBack exposes six separate nodes (app icon, name, package, time,
  "Status: …", "Edit") and announces none of them as a button.
- `DeviceAppItem.kt:34-36`
- `SchedulerScreen.kt:164` and `:183`

`Role.Button` and `onClickLabel` would tell a screen-reader user these are actionable and what the
action does.

**Impact:** every list row and both picker triggers are announced as unlabelled content rather than as
controls. Combined with UX-11, the Home list is genuinely confusing under TalkBack.

### UX-11 — Decorative icons carry descriptions; the "Edit" icon looks actionable but isn't — **Medium**

Distinguishing the two failure modes the phase asks about — **nothing in this codebase omits
`contentDescription` by accident** (5 `Icon`/`Image` call sites, all 5 supply one). The problem is the
opposite: descriptions are supplied where `null` is correct.

- `AppIcon.kt:35` — `contentDescription = appName`. At both call sites
  (`ScheduledAppItem.kt:52-55`, `DeviceAppItem.kt:39-42`) the app's name is rendered as adjacent text,
  so TalkBack reads the name twice per row. Should be `null` (decorative).
- `ScheduledAppItem.kt:88-92` — an "Edit" pencil `Icon` with `contentDescription = "Edit"` that is
  **not itself clickable**; the whole row is the click target. TalkBack announces a static image called
  "Edit", implying a button that doesn't exist. Should be `null`, with the row carrying
  `onClickLabel = "Edit schedule"`.
- `AppIcon.kt:41-48` — the no-icon fallback `Box` is correctly silent.
- `SchedulerScreen.kt:170` / `:189` — `contentDescription` duplicates the adjacent
  "Select time"/"Select date" label verbatim; also should be `null` once the row is merged.

**Impact:** stuttering, misleading TalkBack output on the main list.

### UX-12 — Five hardcoded user-facing strings, and a raw enum shown to the user — **Medium**

Exhaustive list (grep `Text("` / `contentDescription = "`, all confirmed by reading):

| # | Location | String | Note |
|---|---|---|---|
| 1 | `TimePickerDialog.kt:35` | `"OK"` | `R.string.ok` already exists and is used by `DatePickerDialog.kt:40` |
| 2 | `TimePickerDialog.kt:40` | `"Cancel"` | `R.string.cancel` already exists and is used by `DatePickerDialog.kt:45` |
| 3 | `ScheduledAppItem.kt:81` | `"Status: ${app.status}"` | see below |
| 4 | `ScheduledAppItem.kt:90` | `contentDescription = "Edit"` | resolved by UX-11 |
| 5 | `HomeScreen.kt:71` | `contentDescription = "Add"` | vague even in English; "Schedule an app" |

Item 3 is the worst: `app.status` is the persisted `ScheduleStatus` enum **name**
(`ScheduleStatus.kt:8-13`, written at `SchedulerViewModel.kt:167`), so the user literally sees
`Status: SCHEDULED` / `Status: EXECUTED` / `Status: CANCELLED` / `Status: FAILED` — screaming-caps
identifiers, untranslatable by construction.

Note `TimePickerDialog.kt` is the *only* file that regressed here; `DatePickerDialog.kt` next to it does
it correctly. This is a localised slip, not a codebase-wide habit.

Related, from the baseline: `strings.xml:23`
(`another_app_is_already_scheduled_at_this_time_please_select_a_different_time`) is flagged
`UnusedResources` — a conflict message exists but the shorter
`an_app_is_already_scheduled_at_this_time` is used instead (`SchedulerScreen.kt:306`).

### UX-13 — `Color.Gray` on the light surface fails the 4.5:1 contrast minimum — **Medium**

`DeviceAppItem.kt:48`:

```kotlin
Text(text = app.packageName, fontSize = 14.sp, color = Color.Gray)
```

`Color.Gray` is `#FF888888` (relative luminance 0.246). Against the light surface (`#FFFBFE`, luminance
0.985) the contrast ratio is **3.49:1** — below the 4.5:1 WCAG AA minimum for 14sp body text. It also
ignores the theme entirely, so it does not adapt under dark mode or dynamic color (where it lands at
~4.8:1, marginally passing, by luck rather than design). The sibling component,
`ScheduledAppItem.kt:70`, does this correctly with `MaterialTheme.colorScheme.onSurfaceVariant`.

Same line and `DeviceAppItem.kt:47` also hardcode `18.sp`/`14.sp` and `FontWeight.Bold` instead of
`MaterialTheme.typography` — the only two type escapes in the codebase.

### UX-14 — Long app names push the Edit icon off screen — **Medium** (unverified)

`ScheduledAppItem.kt:37-93`: the outer `Row` is `fillMaxWidth()` with
`horizontalArrangement = SpaceBetween`. Its first child is an inner `Row` with **no `Modifier.weight`**,
so it is measured first against the full width; the `Text` at `:61-66` is `maxLines = 1` +
`TextOverflow.Ellipsis` and will happily consume all of it. The trailing `Icon` at `:88` is then
measured against the remainder — zero — and collapses.

`DeviceAppItem.kt:47-48` has the opposite problem: no `maxLines`/`overflow` at all, so long names and
package names wrap to arbitrary height.

**Impact:** the edit affordance disappears for apps with long names. **Unverified:** render
`ScheduledAppItem` with a 60-character app name, or install an app with a long label.

### UX-15 — Exact-alarm permission check is gated on API 33 but the API is 31 — **Medium**

`SchedulerScreen.kt:119`:

```kotlin
if (isAndroidTIRAMISUOrLater() && !alarmManager.canScheduleExactAlarms())
```

`isAndroidTIRAMISUOrLater()` is `SDK_INT >= 33` (`SdkExtensions.kt:12`), but
`canScheduleExactAlarms()` was added in **API 31** and the user-revocable Special App Access it reflects
exists from Android 12. `ContextExt.kt:18` gets the boundary right (`>= Build.VERSION_CODES.S`), so the
two halves of the same feature disagree.

**Impact:** on Android 12 and 12L (API 31/32), a user who revokes "Alarms & reminders" in Settings gets
no prompt and no explanation — scheduling just fails. minSdk is 24, so this is a live range.

### UX-16 — POST_NOTIFICATIONS is requested with no rationale and no denied path — **Medium**

`MainActivity.kt:44` calls `requestNotificationPermission()` from `onCreate`, before `setContent`.
`MainActivity.kt:77-89` uses the legacy `ActivityCompat.requestPermissions` with request code 100, and
**`onRequestPermissionsResult` is never overridden** — nothing anywhere in the codebase reads the
result. There is no `shouldShowRequestPermissionRationale` check and no follow-up if the user denies.

The app's entire feedback channel for a fired schedule is a foreground-service notification
(`AppLaunchService.kt:44`, `RescheduleService.kt:56`), including its failure messages
(`R.string.failed_to_launch_app`, `R.string.app_not_installed`).

**Impact:** the permission prompt fires cold on first launch with zero context — the pattern most likely
to be denied — and after denial the app silently loses its only way to report that a schedule fired or
failed. Also, `rememberLauncherForActivityResult` is used correctly for the overlay permission
20 lines away (`MainActivity.kt:93-97`), so the legacy API here is inconsistency, not constraint.

### UX-17 — No dark-mode window theme; white flash on launch in dark mode — **Medium**

`res/values/themes.xml` has one style:

```xml
<style name="Theme.AppScheduler" parent="android:Theme.Material.Light.NoActionBar" />
```

There is no `res/values-night/` directory (confirmed by `ls -R app/src/main/res`). The **Compose** theme
is fine — `Theme.kt:36-58` wires `isSystemInDarkTheme()`, `darkColorScheme`, and dynamic color for
API 31+ correctly — but the *window* background used for the starting window is unconditionally light.

**Impact:** a white flash before the first Compose frame every launch on a dark-mode device. Also, the
parent is a **platform** `android:Theme.Material.*`, not `Theme.Material3.*`/AppCompat, so there is no
splash-screen configuration surface.

### UX-18 — Times are always formatted 12-hour, ignoring the device's 24-hour setting — **Medium**

`AppConstant.kt:16` fixes `TIME_12H = "hh:mm a"`, used by `LocalTime.toFormattedTime`
(`DateTimeExtensions.kt`, default parameter) and by `SchedulerViewModel.kt:73`. Meanwhile
`rememberTimePickerState` (`TimePickerDialog.kt:24`) defaults `is24Hour` to
`DateFormat.is24HourFormat(context)` — the system setting.

**Impact:** a user with 24-hour time enabled picks "17:30" in the dial and the screen then displays
"05:30 PM". The picker and the display disagree with each other and one of them disagrees with the
user's system preference. Affects most of Europe and Asia.

### UX-19 — No screen titles, no back affordance, no pane titles — **Medium**

There is no `TopAppBar` anywhere in the app (grep: zero hits). None of the three screens displays its
own name, and neither `DeviceAppsListScreen` nor `SchedulerScreen` offers a visible back control — only
system back, routed through `NavDisplay(onBack = …)` at `AppSchedulerNavHost.kt:58-62`. No screen sets
`Modifier.semantics { paneTitle = … }`.

**Impact:** on navigation, TalkBack has no title to announce, so screen changes are silent. Sighted
users on gesture-nav devices get no visible way back. (Predictive back itself looks fine: targetSdk 36
enables it by default, `Navigator.goBack()` at `Navigator.kt:11-15` correctly guards `size > 1`, and
there is no custom `BackHandler` to break it.)

### UX-20 — All user feedback goes through Toast; the loading overlay doesn't block input — **Low**

`SchedulerScreen.kt:288-360` routes all eight `ScheduleContract.Effect` cases to `Toast.makeText`.
Toasts are unanchored, uncontrollable in duration, offer no undo or retry, and are the weakest option
for error reporting; `Snackbar` via a `SnackbarHostState` is the Material 3 answer. Note the screen has
no `Scaffold`, so there is nowhere to host one today.

Separately, `SchedulerScreen.kt:229-231` overlays `CommonCircularProgressIndicator` on the full screen
while loading, but with no scrim and no input blocking — the underlying Save button stays tappable.
`ActionButtons` debounces (`SchedulerScreen.kt:255-256`, `ExtensionsUI.kt:13-26`), which mitigates it,
and `CommonCircularProgressIndicator.kt:25-31` sets no `contentDescription`/progress semantics so the
loading state is invisible to TalkBack.

### UX-21 — No adaptive layout; single-column everywhere — **Low**

Zero hits for `WindowSizeClass` / `currentWindowAdaptiveInfo` across the codebase. All three screens are
full-width single columns. Nothing is locked to portrait (no `screenOrientation` in the manifest), which
is correct, but on a tablet or unfolded foldable the app-list rows stretch to full tablet width and the
Scheduler screen is a narrow strip of content in a large empty space.

**Impact:** poor but functional on large screens. Listed for completeness, not as a defect to rush.

### UX-22 — App list is sorted with `String.sortedBy`, not a locale `Collator` — **Info**

`DeviceAppsRepositoryImpl.kt:37` — `.sortedBy { it.name }` uses natural UTF-16 code-unit ordering, which
mis-sorts accented and non-Latin app names. Only visible in non-English locales, of which there are
currently none in the project (single `values/` directory, no `resConfigs`).

## Explicitly checked and found clean

- **RTL.** `android:supportsRtl="true"` (`AndroidManifest.xml:20`); zero uses of `left`/`right`
  alignment or padding; `Arrangement.Start` / `Alignment.Start` / `padding(horizontal=)` throughout.
  The two vector drawables (`clock_24.xml`, `edit_square.xml`) are symmetric enough not to need
  `autoMirrored`.
- **`sp` for text.** No `dp` text sizing anywhere. `Type.kt` overrides only `bodyLarge` and uses `sp`
  for size, line height, and letter spacing.
- **`enableEdgeToEdge()`** is called, correctly, from `ComponentActivity` at `MainActivity.kt:42`
  — so system-bar icon appearance is auto-handled and the manual
  `isAppearanceLightStatusBars` dance the skill warns about is not needed.
- **IME insets: not applicable.** There is **no `TextField`, `OutlinedTextField`, or `BasicTextField`
  in the entire codebase** (grep: zero hits). The absence of
  `android:windowSoftInputMode="adjustResize"` in the manifest is therefore harmless today. The one
  residual IME surface is Material 3 `DatePicker`'s text-input toggle
  (`DatePickerDialog.kt:49`), which opens a keyboard inside a dialog window — **unverified** whether
  the IME occludes it; check by tapping the pencil icon in the date picker on a small screen.
- **Dynamic color** is wired for API 31+ with light/dark variants (`Theme.kt:43-51`) and a real
  `darkColorScheme` fallback (`Theme.kt:14-18`) — the Compose theme layer is correct. The
  `Purple80`/`Pink40` values in `Color.kt` are unmodified template defaults, which is a branding gap,
  not an accessibility one, and they only apply below API 31.
- **Predictive back** — see UX-19; no custom `BackHandler`, `NavDisplay` handles it.
- **List keys** — `HomeScreen.kt:83` supplies a stable `key = { it.id }`. (`DeviceAppsListScreen.kt:78`
  does not, but that's a Compose-phase concern.)
